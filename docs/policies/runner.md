# Policy: fixer runner (autonomy mode)

> Part of the autonomy pack (ADR 0011). A new project does not have it until `python3 scripts/pack.py add autonomy` (choose-path runs it when you pick autonomy mode).

> One open issue, one sandboxed agent per attempt, the gate decides, merges go to a staging branch only. Design: docs/decisions/0009-fixer-runner.md. Needs the ledger (docs/policies/issue-ledger.md) and the gate (docs/policies/merge-gate.md).

## Start a run
1. Set `factory.json` `autonomy.enabled` to `true` (it is `false` by default: nothing here runs, and no gate check changes, until you do). Settings: `staging_branch` (staging), `max_attempts` (3), `daily_budget_usd` (5), `run_budget_usd` (2), `model` and `review_model` (sonnet), `max_turns` (40), `attempt_estimate_usd` (0.5, the cost guess before any attempt exists). On Linux the Bash sandbox needs `bwrap` and `socat` (same as evals).
2. Have a clean working tree, an approved PRD for the issue, and the issue in `issues/open/` (`python3 scripts/issues.py find`; commit it).
3. `python3 scripts/runner.py run --next` (lowest open issue whose PRD is approved) or `--issue ISS-0007`. Add `--dry-run` to see the choice and the budget without spending. `--model haiku` and `--max-attempts 2` override the settings for one run. You start every run; nothing starts one for you.
4. `python3 scripts/runner.py status` (or the dashboard Autonomy tab) shows runs, attempts, first-try pass rate, rework per fixed issue, cost per fixed issue, spend today against the cap, parked issues with their last codes, and how far staging is ahead of main.

Exit codes: 0 fixed and merged (or nothing to do), 1 parked, 2 refused or usage error, 3 stopped by a budget cap.

## What a run does
Per attempt, at most `max_attempts`:
1. A fresh worktree from the tip of `staging` at `.claude/worktrees/runner-ISS-n` on branch `fix/ISS-n`. `staging` is created from your current branch if missing; when your branch has moved ahead, it is merged into `staging` first (a conflict stops the run).
2. A headless fixer (`claude -p`) works there in the eval sandbox: allow-listed environment, throwaway HOME and TMPDIR, Bash sandbox without network, `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB=1`, `acceptEdits` with an explicit tool list. The prompt holds the issue file, the PRD path, the rules, and from attempt 2 the previous gate reasons and reviewer notes.
3. The runner commits the result itself with its own trailers (`Refs: ISS-n`, `Fixer-Attempt: k`, `Runner: <run>`). A commit the fixer made on its own is squashed away. A change to `gate.protected` or to the gate and runner machinery (`RUNNER_PROTECTED` in scripts/runner.py: factory.json, `.claude/`, `issues/`, `metrics/`, gate.py, acceptance.py, runner.py, sandbox.py, issues.py, metrics.py, check.sh) is reverted and the attempt fails with `fixer-touched-protected`. A fixer therefore cannot produce an `Acceptance-Change` or `Review` trailer (TD-012 for unattended work).
4. After the commit the runner evaluates a FRESH checkout of it (so ignored or untracked leftovers of the fixer's tree cannot matter), and everything that executes fixer-written code (the acceptance suite, build, lint, tests) runs in the tree sandbox: scrubbed environment without the model credential, bubblewrap without network, throwaway HOME, the main project directory hidden, scripts and gate inputs read-only. Without bwrap the runner refuses. The issue's own tests must pass (`issue-not-fixed` otherwise; the gate's baseline check does not cover tests that were failing when admitted). Then a second agent reviews the diff in its own fresh checkout with only Read, Glob and Grep (`--tools`, permission mode `dontAsk`) and ends with a JSON line `{"verdict": "ship"|"fix-first", "nonce": ...}`; the runner writes the `Review:` trailer from it (anything else counts as fix-first, `review-unparsed`). A diff over 40000 bytes fails the attempt (`diff-too-large`), and a reviewer that changed its checkout fails it (`reviewer-modified-tree`).
5. `gate.py` runs in the worktree with `review: required` (the runner's own gate module judges, not the fixer's copy).
6. Pass: `fix/ISS-n` is merged into `staging` with `--no-ff`, `issues.py sync` moves the issue to `issues/fixed/`, rows and ledger are committed on staging, the worktree is removed. Fail: the next attempt starts again from the staging tip with the reasons.

After the cap the issue moves to `issues/blocked/` with an attempt log and the last gate reasons, and nothing merges (the branch `fix/ISS-n` stays so you can read the last attempt). `python3 scripts/runner.py unpark ISS-n` puts it back in `issues/open/` after you acted (a PRD clarification, a test fix, a manual change). The finder does not file a duplicate for a parked issue.

## Parallel fixers and scheduled runs (AUTO-6, ADR 0010 C6)
`python3 scripts/runner.py run --next --parallel N` works N issues at once. N runs from 1 to `autonomy.max_parallel` (default 1, so parallel is off until you raise it; hard cap 4 whatever you set); anything else is refused. It picks open issues of approved PRDs that share no failing test and no fingerprint, so two fixers never chase the same thing, and needs `--next` (not `--issue`). Each issue gets its own worktree, branch and fixer; every per-attempt safeguard above applies unchanged (fresh-checkout evaluation, tree sandbox, read-only reviewer, identity checks, protected paths). `--dry-run` shows the batch.
- **Merges are serial.** One lock guards merging to `staging`. A fix that passed on the tip it started from merges straight away if `staging` has not moved. If another fix merged in the meantime, this one is rebased onto the current tip and its tests and the gate run again on a fresh checkout of the result (`regated_on` in its row), and only then does it merge. A conflicting rebase or a failed re-gate ends the attempt with the code `stale-after-merge`: it counts as a failed attempt, and the next one starts from the new tip with the reasons.
- **One budget.** Before each paid call the runner checks `daily_budget_usd` (and `run_budget_usd`, which covers the whole parallel run) against all spend so far plus the estimate of every attempt still running. Two fixers cannot together pass the cap; a fixer that does not fit stops before it pays (exit 3, issue stays open). Rows are appended one at a time to `metrics/runner.jsonl`; a `parallel` row records the fixers used and the most seen working at once. `status` and the dashboard Runner block show parallel runs, max concurrency and the `stale-after-merge` count.
- **One runner at a time still holds**: the lock file covers the whole parallel run.

**Scheduled runs.** The template never creates a schedule. `--scheduled` marks a run as started by a scheduler; it is refused unless `autonomy.schedule_ok` is `true` (default `false`: your standing go for unattended runs, and you can revoke it by setting it back). Even then it only works issues of PRDs that are approved AND whose backlog item is `[~]` (in progress) in docs/BACKLOG.md. To schedule one yourself, set `autonomy.enabled` and `autonomy.schedule_ok` to true, commit a clean tree on the branch to build on, and start the command from your own scheduler, for example cron on a machine that has `claude`, `bwrap` and `socat`:
```
17 */4 * * *  cd /path/to/project && python3 scripts/runner.py run --next --parallel 2 --scheduled >> .factory/runner-cron.log 2>&1
```
or a scheduled Claude Code routine that runs the same command. Spend stays bounded by `daily_budget_usd`; nothing is pushed or promoted (the promotion steps above stay yours).

## Caps
The budget is checked before every paid call, never after: before an attempt, stop if today's spend plus the estimate (the mean attempt cost, or `attempt_estimate_usd` for the first) would pass `daily_budget_usd`, or this run's spend plus the estimate would pass `run_budget_usd`; before the reviewer, stop if the fixer used up what was left. Each call gets `--max-budget-usd` with the remaining budget. A call that reports no usage (timeout, crash) is booked at the estimate with `cost_estimated: true`. `acceptance.py second-reading` checks and books against the same daily cap. A stop keeps the results so far, prints why, and leaves the issue open (exit 3). An attempt costs the fixer plus the reviewer. `metrics/runner.jsonl` (tracked, committed on staging) holds one row per attempt, park, stop, unpark and second reading; the daily total reads it from the working tree and from staging, so a checkout of main still sees today's spend. Days are UTC.

More: promoting staging to main, release verification and learning are in docs/policies/runner-release.md; second reading and the honest limits are in docs/policies/runner-safety.md.
